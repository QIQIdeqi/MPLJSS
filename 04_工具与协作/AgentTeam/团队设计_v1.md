日期：2026-10-31（北京时间）

状态：2026-10-31用户授权落地，根AGENTS已加入团队调度规则，当前主聊天担任制作人，执行入口见[执行说明](执行说明.md)。首次只读试运行已完成，后续修复与制作按当前授权执行。完整岗位池与写入归属已补入执行说明，覆盖主理人、PM、战斗、各美术分工与玩家体验。采用原生指令调度，未安装自定义Agent文件、接管旧聊天或启用自动化。下文“建议”和设计阶段边界保留为方案说明，当前执行范围以根AGENTS和执行说明为准。

## 1. 目标与组织

用户给出目标，制作人拆解并组织专业 Agent，收齐结果后形成一份反馈。用户保留创作方向、关键玩法取舍与项目优先级的最终决定权；制作人负责授权范围内的执行取舍、进度、依赖与交付质量。

```text
用户：方向、体验目标、关键决策
                  ↕
制作人：唯一主入口，拆解 → 调度 → 整合 → 验收 → 反馈
    ├─ 关卡策划
    ├─ 系统策划
    ├─ 数值策划
    ├─ 美术与技术美术
    ├─ Unreal 工程
    ├─ QA 与体验验收
    └─ 发行与协作支持（按需）
```

这是岗位池，不是同时常驻八个进程。本次会话可用四个并发槽，采用制作人加最多三个子代理；涉及依赖的工作分批执行。简单解释和单点改动由制作人直接完成。

## 3. 岗位卡：任务、交付与边界

| 岗位 | 必须解决的问题 | 交付 | 边界 |
| --- | --- | --- | --- |
| 制作人 | 这轮服务什么体验？先做什么？依赖是什么？是否交付？ | 目标、任务分配、整合结论、证据、下一步 | 不自行改变用户确定的创作方向；不把代理意见直接当成已确认规则 |
| 关卡策划 | 玩家去哪里、看见什么、学会什么、如何作出选择？ | 动线、遭遇、空间尺寸、节奏、可玩验收点 | 涉及系统和数值变更时提出需求，由对应岗位核对 |
| 系统策划 | 规则如何触发、消耗、结算与退出？ | 状态流程、输入输出、规则及异常路径 | 不把新玩法建议自动变成当前需求 |
| 数值策划 | 参数是否支持目标体验、经济是否闭合？ | 参数表、公式、假设、算例、需要实测的范围 | 不将推算写成实测，不擅自改核心规则 |
| 美术与技术美术 | 表现是否清楚、一致、可接入？ | 源素材、规格、来源、接入要求和引擎截图 | 维持人物尺度、项目配色、前后遮挡；特效优先适配PixelFX |
| Unreal工程 | 设计怎样完整落地到可运行版本？ | 实现、资源接入、必要检查、操作入口与构建 | 复用现有工程；遵循stop-that-shit与ponytail full |
| QA与体验验收 | 实现是否满足本轮标准？证据覆盖到哪？ | 通过/失败/未验证、复现、截图与日志位置 | 自动测试不等于真人体验、听感、平衡或性能验收；可提出阻塞问题 |
| 发行与协作支持 | 成果如何被找到、使用和交付？ | 版本说明、文档链接、来源许可、发布核对 | 仅执行本轮或既有授权内的发布与外部消息操作 |

音频、叙事等任务按内容交给美术/系统岗位，必要时临时增加专业角色，不常驻新增管理层。

## 4. 一次任务如何流转

1. 制作人从用户请求确定解释、审查、观察或修改模式，检查相关现行文档、文件状态与正在进行的工作。
2. 给每个必要岗位明确目标、输入、允许修改的路径、依赖、验收标准和回报内容。缺少会影响关键决策的信息时才向用户提问；其余在范围内推进。
3. 独立分析可并行。规则先于参数，设计先于实现；美术制作可在规格确定后与程序并行。
4. 每个文件同一时间只有一个写入负责人。共享UE地图、资源、构建输出和编辑器操作串行；不覆盖其他聊天的未提交修改。子代理不自行提交、推送或改团队规则，统一交给制作人按授权处理。
5. QA依据最终版本检查明确验收点。失败回到对应负责人修复；检查被环境阻塞时报告真实缺口。
6. 制作人核对规则、素材、代码、文档的一致性，并给出交付结论。专业岗位的意见出现冲突时，制作人提供推荐、理由和影响；只有超出既定方向或授权的关键取舍需要用户决定。
7. 完成必要文档和项目memory记录，统一向用户反馈，附三个可直接回复的后续提示。

不得把启动子代理、收到总结、生成素材、编译通过、打包通过或完成发布混为同一个完成状态。

### 制作人派单格式

```text
任务：
用户目标与本轮范围：
负责人：
现行输入及路径/版本：
允许修改：
依赖与暂不可改动项：
交付物及SSD目标目录：
验收标准：
回报：结果、修改文件、证据、未覆盖项、阻塞及跨岗位影响。
```

### 制作人最终反馈格式

```text
本轮结论：完成 / 部分完成 / 阻塞，以及对玩家或项目的实际影响。
交付：文件、素材、可运行入口或版本链接。
验证：实际执行和通过的检查；必要的未验证范围。
需要你决定：仅列真正需要用户取舍的事项，没有则省略。
建议下一步：一个当前最有价值的行动。
三个回复提示：推进 / 调整 / 验收方向的具体指令。
```

制作人应形成一个有依据的推荐，不只转发多份互相冲突的岗位报告。用户可展开查看专业意见和证据。

## 5. 共同资料与存放

- 场景、关卡、系统、数值：`00_Doc/协作策划/` 内对应正文，wolai仅存其Git链接。
- 角色、怪物、原文案：继续由wolai维护；跨平台引用时标明来源，不另建一份竞争正文。
- 工程、工具、原始美术和接入说明：复用`02_Prototype/AlchemyHD2D/`现有分类。
- 可交付构建：`03_Build/`；正式发布记录复用`00_Doc/版本发布/`。
- 团队规则与以后必要的任务交接：`04_工具与协作/AgentTeam/`；具体任务产生时再建交接文件，避免复制全部策划。
- 项目记录：北京时间`memory/YYYY-MM-DD.md`。其他工作区的执行记录存回对应SSD工作区。
- 初版设计阶段只新增方案与memory的范围属于历史；现行写入范围以当轮用户授权和派单为准，不能覆盖其他聊天的改动。

历史聊天帮助理解决策；当前拥有维护权的文档和实际实现用于核对现状。明确区分已确认、提案、已实现和已验证。

## 6. 历史：首轮试运行建议（已执行）

初版建议的口令如下，保留作为历史派单示例：

> 按团队方案启动一次只读试运行。你担任制作人，安排关卡、系统/数值、工程/美术三个子代理，检查当前村庄到Boss完整流程，读取相关现行资料，列出最影响玩家体验的三个问题。等待全部结果后，由制作人给我优先级、证据和下一步，不修改玩法、不发布。

这样可以先验证分工和统一反馈，随后再针对一个明确问题进入制作。首次试运行不自动接管其他正在工作的聊天。

精简调度规则现已纳入根AGENTS，完整岗位池见执行说明。旧聊天没有被物理合并或自动监听；四槽按需分批执行，不为每个岗位建立常驻进程。
