# 可实现的系统规则

在撰写可落地规格、检查规则冲突或交付研发时阅读。只细化实际涉及的状态和边界。

## 一条规则应回答的问题

- 谁发起，哪些对象参与，是否必须满足前置条件。
- 消耗何时扣除，是否允许取消，失败或中断时怎样处理。
- 输入如何改变状态，奖励何时生成，处理是否可以重复。
- 多个效果同时触发时如何排序，效果叠加、覆盖或互斥。
- 随机结果在哪个阶段确定，玩家能知道什么信息。
- 存档或重新进入后，什么状态必须保留。

连续动作系统还需明确输入窗口、动作锁定、可取消阶段、碰撞与命中的结算点。联网系统按实际需求明确哪些结果由服务器决定；不要把单机规格写成分布式系统方案。

## 规则表达示例

模糊表达：“升级需要足够材料，失败给予适当补偿。”

可执行表达：“确认升级时检查并扣除材料；材料不足不改变状态。升级结果由当前成功率抽样。成功增加等级，失败保持等级并返还规定数量材料。只有结果展示结束后才允许再次提交。”

此示例只说明规格精度，不意味着推荐随机升级。是否存在失败、返还比例或重复提交风险应按目标项目确定。

## 不变量与代表性情境

选择当前系统必须保持的性质，例如库存不为负、任务奖励只领取一次、容量上限下资源如何处理。把性质转成具体情境，而非只说“系统应稳定”。

描述普通成功流程和最相关的异常：刚好足够材料、临界状态、同时触发、操作中断、奖励超出容量。表格适合对比时使用当前环境规定的展示方式，不让模板决定交付形式。

规则评审检查三件事：同一输入是否有明确解释；玩家是否可以理解原因；研发是否还必须自行发明影响体验的规则。保留可配置参数，避免把尚未验证的数值写死成设计不变量。
